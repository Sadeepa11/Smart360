1. Executive Summary & Architecture Overview

SmartCity360 is an enterprise-grade digital platform developed by UrbanTech Solutions to centralize city administration, IoT sensing telemetry, infrastructure control, and citizen services. To ensure flexibility, loose coupling, runtime extensibility, and memory efficiency, five primary Gang of Four (GoF) design patterns have been engineered into the system architecture:

2. Part A: Dynamic Security Wrappers for Data Streams (Decorator Pattern)

2.1 Pattern Identification and Justification (3 Marks)

Selected Pattern: Decorator Pattern (Structural)
Justification: The energy monitoring subsystem requires telemetry data to be wrapped dynamically with features such as AES-128 Encryption, SHA-256 Authentication signatures, and GZIP Compression without modifying the core transmission pipeline (MeterDataStream). Using inheritance would require $2^3 = 8$ subclasses, causing severe class explosion. The Decorator pattern satisfies the Open/Closed Principle (OCP) and Single Responsibility Principle (SRP) by composing wrappers dynamically around the core stream.

2.2 Flexible and Layered Enhancements Mechanism (4 Marks)

All stream components share the common DataStream interface. The DataStreamDecorator abstract class maintains a reference to a wrapped DataStream instance. Outbound operations (writeData) process layers outwards, and inbound operations (readData) unpack layers in reverse.

2.3 Long-Term Benefits in Reusability and Extensibility (8 Marks)

  • Zero Breaking Changes: New wrappers (e.g. Brotli or Kyber Quantum Cryptography) can be introduced without modifying existing stream code.
  • Runtime Reconfiguration: High-bandwidth meters can leverage full compression and encryption, while low-power battery nodes can dynamically drop compression to conserve energy.
  • Independent Unit Testability: Each security concern is validated in complete isolation.

3. Part B: Hierarchical Structure of Smart Zones (Composite Pattern)

3.1 Pattern Identification and Justification (3 Marks)

Selected Pattern: Composite Pattern (Structural)
Justification: Municipal assets naturally follow a tree hierarchy: City → District → Street → Building. The Composite Pattern allows client code to treat leaf elements (individual Buildings) and composite containers (Streets, Districts, Cities) uniformly through the ZoneComponent interface.

3.3 Scalability for Large and Growing City Infrastructure (8 Marks)

  • Recursive Delegation: Issuing colomboMetro.shutdownPower() automatically traverses and deactivates all child components down to the leaf buildings without explicit iterative looping by the client.
  • Arbitrary Tree Depth: Intermediate levels (such as Wards, Sectors, or Floors) can be added without modifying the traversal algorithms.
  • Aggregation Simplification: reportUsage() sums power metrics upwards through the hierarchy in real time.

4. Part C: Escalation of Citizen Complaints (Chain of Responsibility)

4.1 Pattern Identification and Justification (3 Marks)

Selected Pattern: Chain of Responsibility Pattern (Behavioral)
Justification: Complaints submitted by citizens vary widely in severity (LOW, MEDIUM, HIGH, CRITICAL). Direct coupling between the submission portal and specific municipal officers would lead to rigid, unmaintainable code. The Chain of Responsibility pattern decouples the request sender from the receiver by passing complaints along a chain of candidate handlers until one resolves it.

4.2 Decoupled Request Handling Mechanism (4 Marks)

Handlers maintain a successor reference (nextHandler). Each handler checks canHandle(complaint): if true, it resolves the issue; if false, it delegates along the chain: LocalStaffHandler → SupervisorHandler → CityManagerHandler.

4.3 Evaluation of Flexibility vs. Traceability (8 Marks)

  • Flexibility Advantages: Handlers can be dynamically inserted, removed, or re-ordered at runtime (e.g. adding an Emergency Disaster Coordinator during weather alerts) with zero disruption to existing handlers.
  • Traceability & Auditability: To prevent requests from being silently dropped, our implementation embeds an audit trail inside the Complaint object (recording resolvedBy and timestamped resolution notes) and provides fallback reporting for unhandled requests.

5. Part D: Efficient Management of Smart Street Lights (Flyweight Pattern)

5.1 Pattern Identification and Justification (3 Marks)

Selected Pattern: Flyweight Pattern (Structural)
Justification: A municipal grid comprises tens of thousands of streetlights. Each fixture has identical physical specifications (bulb type, wattage, lumen output, firmware, calibration data), varying only by GPS coordinates and operational dimming. Storing these specifications inside every object creates massive heap redundancy. The Flyweight Pattern shares common immutable intrinsic state to optimize memory footprint.

5.2 Separation of Intrinsic vs. Extrinsic State (4 Marks)

State Classification Properties Storage Location
Intrinsic (Shared) Model name, Wattage, Color Kelvin, Lumens, Firmware, 2KB Spectral calibration array. Shared immutable StreetLightType Flyweight instance.
Extrinsic (Unique) Light ID, GPS Latitude, GPS Longitude, Power State, Brightness %. Passed in runtime context or stored in lightweight StreetLight instance.

6. Part E: Interpreting City Policies Defined in DSL (Interpreter Pattern)

6.1 Pattern Identification and Justification (3 Marks)

Selected Pattern: Interpreter Pattern (Behavioral)
Justification: City regulations (noise thresholds, parking limits, pollution advisories) are subject to frequent legislative amendments. Hardcoding these rules as conditional Java code requires recompiling and redeploying production services. The Interpreter Pattern parses human-readable DSL rules into an Abstract Syntax Tree (AST) that is evaluated dynamically against incoming sensor context.

6.3 Suitability for Rule Updates and Extensibility (8 Marks)

  • Runtime Reconfiguration: Non-technical municipal managers can update rules (e.g. noise_level > 65 AND hour >= 21) dynamically without altering backend bytecode.
  • Grammar Extensibility: Supporting new operators (e.g. BETWEEN or IN_RADIUS) merely requires adding a new concrete class implementing Expression.
  • Evaluation Scope: Ideal for targeted domain mini-languages; larger, general-purpose languages are better addressed with tools like ANTLR.

7. Part F: VIVA Defense & Video Demonstration Guide

7.1 Examiner VIVA Questions & Expert Answers

Q: What architectural problem would occur if you used Subclassing instead of Decorator in Part A?
A: Subclassing leads to an exponential class explosion ($2^N$). With Encryption, Compression, and Authentication, we would need 8 static subclasses. Decorator eliminates this by allowing arbitrary runtime combination with only 3 wrapper classes.
Q: How does the Flyweight pattern guarantee thread safety when thousands of lights share one type?
A: All fields in StreetLightType are marked final, ensuring strict immutability. Contextual properties (coordinates, power) are kept external. Immutable objects are inherently thread-safe.
Q: In Composite Pattern, why do we implement the component interface on both leaf and composite?
A: This enables polymorphism, allowing client code to invoke methods like shutdownPower() on any node without checking whether it is an individual building or a multi-building district.
